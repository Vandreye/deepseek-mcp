# Benchmark

Runs the same 11 tasks against two (or more) versions of the connector and compares them, so we know whether a change helps.

```
npm run bench -- --versions before=13c8626,now=. --reps 3
npm run bench:compare -- bench/results/<file>.jsonl
```

- Compare settings too: `--versions strict=.,plain=.?DEEPSEEK_STRICT_TOOLS=off` (several settings: `?A=1&B=2`).
- A version is `.` (this working tree, rebuilt) or any git ref. Refs are checked out into `bench/.versions/<sha>` and built once.
- `--tasks review-orders,bugfix-slug` runs a subset; `--parallel 3` runs that many at once; `--budget 3` stops at $3 (peak prices); `--model pro` switches model.
- Results go to `bench/results/<time>.jsonl` (one line per run) and a `.md` summary next to it.

Claude's side, with and without delegating (uses your Claude plan, about $0.12-0.25 per run):
```
node bench/claude-vs-ds.mjs --reps 2 [--tasks review-orders,code-chunk] [--model sonnet]
```

## How it works

Each run starts the version's MCP server (`dist/index.js`) in a fresh copy of a small test project and calls its tools the way Claude Code does. A preload script (`probe.mjs`, via `node --import`) records every request the server makes to DeepSeek, without changing the server. So any old commit can be measured too.

Everything else is the same for every version: the model, the task text and an empty settings folder. User settings are never used. Costs are always priced at peak rates, so the time of day doesn't skew them.

## Tasks

| id | type | passes when |
|---|---|---|
| review-orders | review | finds at least 3 of 4 planted bugs in `src/orders.js` |
| bugfix-slug | bugfix | its own and hidden slug tests pass |
| code-chunk | code | hidden tests for the new `chunk()` pass |
| tests-money | tests | the new tests pass, and they fail on a broken `formatMoney` |
| research-upload | research | names `upload.js` and the 5 MB limit |
| research-web | research + web | answers Node 20 and cites a URL |
| review-legacy-high | review, high effort | finds at least 2 of 3 planted vulnerabilities in 18 legacy files |
| review-legacy-capped | review, high effort, 700-token step cap | same as above. A stress test: steps get cut off, which shows how each version recovers (`cut-off/empty reports` counts final replies that ended at the cap, whether or not the version noticed) |
| fanout-review | review over 3 areas | 3 area sections, with issues found in at least 2 |
| approval-queue | general | the off-allowlist command is queued and does not run |
| ask-upload | deepseek_ask | answers 5242880 |

The test project is generated by `fixture.mjs`. Hidden tests are copied in only after DeepSeek is done.

## What is measured

- **Claude's side (the main goal):** report size in tokens, which is what Claude reads. Also the fixed overhead per Claude session: tool schemas plus server instructions.
- **Quality:** pass/fail and a 0–1 score per task.
- **DeepSeek:** input tokens (cached and new), cache hit rate, output and thinking tokens, and cost.
- **Speed:** wall time, API calls and the slowest call.
- **Errors:**
  - tool errors, redone steps and steps that hit the output cap
  - reports that were cut off, empty, or leaked tool-call markup
  - API retries and 429s, and harness errors
- **Behaviour:** repeated file reads and history shortenings.

## Reading the comparison

DeepSeek's output varies from run to run, so use at least `--reps 3` for decisions. With two versions, each change is marked:
- **better** or **worse:** the two versions' ranges don't overlap.
- **~:** the ranges overlap, so the difference may be noise.

Run versions in the same session; the runner alternates them so changes in API load hit both alike.
